<objective>
Stand up Continuous Integration for the repo: a GitHub Actions workflow that, on every push and pull_request, builds the project and runs the existing Phase 1/2 test suite against an ephemeral MySQL provisioned by Testcontainers — no GHA `services:` block, no standing database. A red suite fails the job and blocks merge. The single CI entrypoint is a new `test:ci` npm script backed by a small Node runner (`src/test/run-with-container.ts`) that boots `MySqlContainer('mysql:8.0')`, hands the suite the container's `mysql://` DATABASE_URL, applies the 3 committed migrations with `prisma migrate deploy`, spawns `node --test`, and always tears the container down. A one-line guard in `src/test/env.ts` (keyed on USE_TESTCONTAINER_DB) is the only behavioral seam — local `npm test` continues to load `.env.testing` exactly as today.

ENGINE NOTE (read before touching anything): this project runs **MySQL 8.0**, not MariaDB. `@prisma/adapter-mariadb` is Prisma's one driver adapter for the whole MySQL/MariaDB family — it wraps the `mariadb` npm client, which connects to MySQL servers. The dependency name is not evidence of the engine, and neither is `PrismaMariaDb` in `src/lib/prisma.ts`. The container module is therefore `@testcontainers/mysql`.

Purpose: A red suite must block merges without any developer machine or standing test database being involved, while the truncating suite can never be pointed at a real DB. This phase wraps the existing suite; it depends on nothing new and can land before Phases 3–8.
Output: `.github/workflows/ci.yml`, `src/test/run-with-container.ts`, the `test:ci` script + `@testcontainers/mysql` devDependency in `package.json`, and the USE_TESTCONTAINER_DB guard in `src/test/env.ts`.
</objective>
