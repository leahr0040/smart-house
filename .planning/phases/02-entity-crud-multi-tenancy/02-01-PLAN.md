## Phase Goal

**As an** authenticated user, **I want to** manage my houses, rooms, and devices via REST with strict per-user isolation, **so that** only I can see and change my own home hierarchy and every new device starts with a valid state row.

*(Derived from the ROADMAP Phase 2 Goal line; this plan delivers the shared toolchain + seam every slice depends on.)*

<objective>
Stand up the Phase 2 toolchain and the shared public_id seam that every House/Room/Device slice builds on: install `@sinclair/typebox` (0.34 LTS line) + `@fastify/type-provider-typebox` (5.x, peer-matched) + `nanoid` (3.x) — all CJS-native, so no `engines.node` floor and no `require(esm)` risk (cross-AI review F2: the unscoped `typebox` 1.x was 5 days old at review time; `@sinclair/typebox` 0.34 is the battle-tested, CJS-native equivalent with an identical `Type.Object`/`Type.Partial`/`Type.Union`/`Type.Literal` API for every schema this phase writes, and it matches the CONTEXT.md discretion note verbatim). Regenerate the Prisma client so the `Device` type and live dev-DB table carry the denormalized `house_id`, add the app-side `public_id` minting hook to the existing extended Prisma client, and create the DB-touching test fixtures plus the first auth test (soft-deleted user cannot log in, TEST-05 auth clause).

Purpose: All three entity slices (Wave 2) depend on the public_id minting hook, the TypeBox type-provider, the regenerated client, and the shared fixtures. Building this once removes duplicated setup and prevents a false-positive verification state (build/type-check pass from the committed schema even when the live table lacks `house_id`).
Output: `nanoid` minter, extended `prisma.ts`, `fixtures.ts` seed/auth helpers, `auth.test.ts`, updated `package.json`.
</objective>
