<objective>
Widen the existing `users.id`, `refresh_tokens.id`, and `refresh_tokens.user_id` columns from `Int` to `BigInt` (D-11: every table uses a uniform `BigInt` integer key so all future FKs and the denormalized `user_id` on Room/Device/Command are the same width — this dissolves the earlier Int-vs-Char(36) mismatch and lays the DATA-02 denormalization foundation). Because Prisma silently switches the generated client's JS representation from `number` to `bigint` the moment these columns change type, this plan MUST also update the existing auth layer so the code still compiles (`npm run build`) and the JWT/response boundaries stay JSON-safe (a raw `bigint` cannot be serialized by `JSON.stringify`, which `@fastify/jwt` and Fastify's response serializer both use). This is the documented behavior-affecting side-effect of the widen — it is maintenance to keep the shipped auth API working, not new feature logic.

The widen is a non-destructive in-place `ALTER TABLE ... MODIFY COLUMN` on MariaDB (fundamentally safer than the Postgres `BIGSERIAL` case in prisma/prisma#18532, which does not apply to MySQL/MariaDB), but it touches a live populated table, so its generated SQL is hand-verified behind a blocking-human gate — mirroring 01-01.

Purpose: Establish uniform BigInt integer keys before any new model or FK is created, without breaking the existing auth flow.
Output: One hand-verified widen migration applied; auth layer bigint-safe; build + existing tests green.
</objective>

      - src/routes/auth/index.ts: at the `/me` handler convert the decoded numeric token id back to bigint for the query, i.e. call `getUserById(BigInt(request.user.id))`; in each of the four response payloads Number-encode the id via `Number(user.id)` so responses stay JSON-safe and the existing `userResponseSchema` (`id: number`) remains valid unchanged. Do not change schemas.ts.

    Document in a short code comment at the JWT boundary that `Number()` encoding is a deliberate, minimal Phase-1 choice safe for the current small autoincrement ids, and that a global BigInt-serialization strategy (or never exposing internal ids) is the Phase 2 decision flagged in RESEARCH Open Question 4.

MODIFY COLUMN` statements: `users.id` to `BIGINT NOT NULL AUTO_INCREMENT`, `refresh_tokens.id` to `BIGINT NOT NULL AUTO_INCREMENT`, and `refresh_tokens.user_id` to `BIGINT NOT NULL`.
