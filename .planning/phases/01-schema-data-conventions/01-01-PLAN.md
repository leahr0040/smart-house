<migration_convention>
**Phase 1 migration rule (per user decision — Phase 1 scope):** while a migration has NOT been pushed to master/main, never create a *new* migration to edit/update columns — amend the existing still-local migration instead. A single migration may span multiple tables. Concretely for this plan: the `User` rename, the `deleted_at` add, and the three Int→BigInt widens are all edits to the same not-yet-pushed migration, so they live together in ONE migration file — they are NOT split into a rename migration + a separate widen migration. If, while iterating, you find another column change is needed on these existing tables before the phase is pushed, amend this same migration (hand-edit + re-run `prisma migrate dev`), do not stack a new one.
</migration_convention>

<objective>
Apply every change to the existing `User`/`RefreshToken` tables in ONE hand-authored migration: rename the populated `User` table to `users` (via `RENAME TABLE`, never DROP+CREATE), add the `deleted_at` soft-delete column to it, and widen `users.id`, `refresh_tokens.id`, and `refresh_tokens.user_id` from `Int` to `BigInt` (`MODIFY COLUMN`, restating `AUTO_INCREMENT`/`NOT NULL`). This delivers the existing-table half of DATA-01 (snake_case `@@map` on the last un-mapped model), the User portion of DATA-03 (soft delete), and the DATA-02 uniform-key foundation (every future FK and the denormalized `user_id` on Room/Device/Command is the same BigInt width — dissolving the earlier Int-vs-Char(36) mismatch). `RefreshToken` already carries `@@map("refresh_tokens")` and the live table is already correctly named (verified against `prisma/migrations/20260617121303_add_refresh_tokens/migration.sql`) — no rename needed there, only the id/user_id widen.

Because Prisma silently switches the generated client's JS representation of these ids from `number` to `bigint` the moment the columns change type, this plan MUST also update the existing auth layer so the code still compiles (`npm run build`) and the JWT/response boundaries stay JSON-safe (a raw `bigint` cannot be serialized by `JSON.stringify`, which `@fastify/jwt` and Fastify's response serializer both use). This is the documented behavior-affecting side-effect of the widen — maintenance to keep the shipped auth API working, not new feature logic.

This is the highest-data-loss-risk work of Phase 1 (it alters live, populated tables), so it ships first, alone, as one migration behind a single blocking-human gate. The MariaDB `MODIFY COLUMN` widen is non-destructive in place (the Postgres `BIGSERIAL` hazard in prisma/prisma#18532 does not apply to MySQL/MariaDB).

Purpose: Preserve all existing auth data while applying the snake_case name, soft-delete column, and uniform BigInt keys — in a single reviewable migration.
Output: One hand-verified existing-tables migration applied; `users` live with `deleted_at`; uniform BigInt keys; auth layer bigint-safe; build + existing tests green.
</objective>
